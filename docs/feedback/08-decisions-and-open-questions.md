## 2. P0 已采用的首期决策基线

以下规则于2026-09-02按实施路线图允许的“书面接受当前推荐默认值”方式采用，作为首期设计约定。后续若业务确认发生变化，必须先更新产品、领域、数据库和验收文档，再修改实现。

### 2.1 关系权重

- 不预设组织级或系统级默认关系权重，避免把某一种组织结构隐含为所有项目的标准。
- HR在项目准备阶段为本项目启用的非自评关系配置权重，并可在发布前调整。
- 当项目存在非自评任务时，自评只用于对照，配置权重为0；参与综合分的非自评关系权重必须精确合计为`100.0000`。
- 当某个被评价人只有自评任务时，自评的计算有效权重为100%。
- 关系权重、适用关系和自评规则在发布时进入不可变快照，发布后不得修改。

### 2.2 关系适用性、未完成任务和计分

- 项目可以为不同被评价人配置不同的适用关系；某关系对某被评价人没有任何评价任务时，记为“不适用”，不计入该人的应完成任务和权重分母。
- 某关系已经生成评价任务，但项目完成时该关系没有已提交答卷，记为“缺失关系”，不能当作0分。
- 报告只使用已提交答卷。对每个被评价人、每个指标，按存在已提交答卷的计分关系权重重新归一化。
- 如果不存在任何已提交的非自评计分关系，即使有自评答卷，也不自动用自评替代他评综合分；只有发布时该被评价人确实仅配置自评任务时，才按自评100%计算。
- 报告必须同时展示任务完成率、不适用关系、缺失关系、原配置权重和实际参与计算权重。

具体公式和手工样例见[领域模型与状态机](./03-domain-model-and-state-machine.md)。

### 2.3 HR原始答案可见范围

- `feedback:progress:view`只允许查看任务数量、评价人、被评价人、关系、任务状态和完成率，不返回答案内容。
- `feedback:report:view`只允许查看已完成项目的汇总和基础报告，不自动获得原始答案。
- `feedback:answer:view`是独立敏感权限，只允许在RuoYi数据范围内查看已提交答案；HR不得查看员工尚未提交的草稿内容。
- HR基础角色默认不包含`feedback:answer:view`。确需审阅原始答案时，由系统管理端把该权限显式授予指定HR角色。
- 首期不承诺真正匿名。获得原始答案权限的HR可以看到评价人身份；所有查询仍受项目归属和被评价人部门数据范围约束并记录操作日志。

权限矩阵见[架构与工程边界](./02-architecture-and-boundaries.md)。

### 2.4 首期报告交付形式

- 首期报告只提供系统内网页表格。
- 首期不提供Excel导入，也不提供Excel、CSV或其他文件形式的报告导出。
- 取消导出的主要原因是减少敏感答案和员工得分脱离系统权限、审计及数据范围控制后的扩散风险，并保持首期范围聚焦。
- 后续若新增导出，必须作为独立范围重新确认字段、脱敏、权限、审计、水印、文件保留和下载访问控制。

### 2.5 其他已采用默认值

- 正式报告统一使用百分制，保留原始题目分值。
- 指标分按指标内实际得分之和除以最高分之和计算。
- 同一关系多人评价时取平均分。
- 指标按权重合成，总权重为100%。
- 首期不允许发布后调整计分规则。
- 首期不向被评价人员工端开放个人报告。
- 首期只自动绑定自评，其他关系由HR手工选择。
- 已完成项目首期不支持重新打开。

## 3. P4已确认技术决策

以下方案于2026-09-02完成技术预检，不改变首期产品范围；详细协议、风险和测试门禁见[P4完整问卷设计器与指标技术预检](./11-p4-questionnaire-designer-precheck.md)。

| 决策 | 当前结论 |
|---|---|
| 草稿接口 | 保持一个问卷草稿GET/PUT聚合接口和服务层单事务，不拆分第二套页面、题目或指标保存体系 |
| 稳定身份 | 页面新增`page_code`；页面、题目、选项和指标用业务Code关联，数据库ID只作为持久化标识并在保存后整体水合 |
| 富文本 | 问卷说明保存受限Tiptap JSON，并由后端提取纯文本摘要；不保存任意HTML，不对题目说明引入富文本 |
| 数值协议 | API正式小数使用最多四位的十进制字符串；前端用四位定点工具，后端用`Decimal/NUMERIC` |
| 指标校验 | 草稿保存硬拒绝结构错误，但允许保存未达发布条件的配置；P4返回后端权威问题清单，P5复用同一校验器阻止非法发布 |
| 排序交互 | 首期使用明确的上移、下移和跨页选择器，不把拖拽库作为P4依赖 |
| 题型复用 | 五种题型共用注册表、编辑、预览、只读、规范化和序列化协议；不为新增题型另建并行设计器 |

## 4. P5已确认技术决策

以下方案于2026-09-02完成决策收口和技术预检，不改变首期产品范围；完整数据契约、API、锁顺序、问题码和测试门禁见[P5人员关系、发布冻结与任务生成技术预检](./12-p5-publication-precheck.md)。

| 决策 | 当前结论 |
|---|---|
| 准备期分配持久化 | 新增长期领域表`fb_evaluator_selection`保存目标、关系和评价人选择，发布后随版本冻结保留；不提前创建正式任务 |
| 正式任务 | `fb_assignment`只在发布事务内由冻结选择物化，任务数必须等于后端权威预览 |
| 默认关系 | 固定建立上级、同级、下级、自己、其他五类；除自己外初始禁用且不设默认权重，自定义关系使用`CUSTOM`类型 |
| 自评规则 | 自己关系始终启用、权重0且不参与常规综合分；每个目标的自评选择由后端派生，客户端不能伪造或删除 |
| 人员与快照 | 候选、保存和发布均复用RuoYi用户数据范围；快照保存发布时的`nick_name`和有效部门，发布后不随改名调岗变化 |
| 聚合配置 | 使用一个发布配置GET/PUT聚合接口保存目标、关系和选择；保存可不完整，但越权、重复和非法引用必须硬拒绝 |
| 发布校验 | 锁内复用P4问卷问题并追加P5人员、关系和任务问题；一次返回稳定、可定位的问题集合 |
| 发布事务 | 固定按项目、问卷版本、人员ID升序加锁，在一个PostgreSQL事务中刷新快照、冻结版本、生成任务并切换项目状态 |
| 发布幂等 | 同项目同版本重试返回既有结果并标记`alreadyPublished=true`；并发请求只有一个执行写入，不引入首期幂等键表 |
| P5/P6边界 | P5用真实PostgreSQL证明任务已生成且可按评价人查询；员工待办正式API和页面仍由P6交付 |
